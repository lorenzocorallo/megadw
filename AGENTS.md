# AGENTS.md - implementation contract

## Mission

Implement the downloader MVP in `PLAN.md` exactly to its phase gates. `PLAN-UPLOAD.md` and `PLAN-STREAMING.md` are deferred specifications: read them for future compatibility, but do not implement them during the MVP.

Priority order:

1. correctness, integrity, security, restart recovery;
2. passing phase gates and deterministic tests;
3. bounded CPU/RAM/FD/disk use on 2 vCPU / 4 GiB;
4. throughput measured by benchmarks;
5. UI polish.

Do not trade a higher item for a lower one.

## Agent operating mode

- Work non-interactively and persist until the current phase gate passes or a concrete external blocker is proven.
- Do not emit an upfront plan, progress narration, or repeated status chatter while implementing.
- Inspect the repository before editing. Reuse existing patterns and dependencies.
- Make reasonable implementation decisions inside the plan's boundaries without asking for permission.
- Do not change architecture, dependencies, protocols, security rules, resource caps, or deferred scope to make a test easier to pass.
- If a required upstream behavior is unavailable or broken, create/update `BLOCKERS.md` with: failing assumption, minimal reproduction, evidence, attempted fixes, and smallest proposed replacement.
- Never weaken or delete a failing test unless the specification itself is demonstrably wrong.
- Finish each phase by running its complete gate commands and reporting only: changed surfaces, commands/results, measured resource data when applicable, and remaining blockers/risks.

## Subagent policy

Use subagents only when work is truly independent and write ownership is disjoint.

Good parallel work:
- read-only upstream/protocol research vs local fixture/test preparation;
- backend implementation vs frontend implementation after the API contract is frozen;
- independent security/test review that does not edit the same files.

Bad parallel work:
- two agents editing the same package;
- scheduler and checkpoint durability implementation in parallel;
- schema and repositories changing concurrently;
- parent + subagents all performing broad repo-wide refactors.

Default maximum: 2 concurrent implementation agents. A third agent is acceptable only for read-only review/research.

The coordinating agent remains responsible for integration and must rerun the full phase gate after merging any parallel work.

## Dependency policy

- Use the exact versions pinned by the repository.
- Vite+ must be a published release, never a preview/commit baseline.
- TypeScript 7 is required.
- TanStack Charts is isolated behind the local throughput-chart adapter and must not leak into domain/API contracts.
- Do not add libraries when the standard library or a small local abstraction is sufficient.
- Do not add a generic transfer framework before upload is implemented.

## Testing discipline

For every behavior change:
- add/adjust the narrow unit or integration test first or in the same logical edit;
- run focused tests while iterating;
- run the entire current phase gate before stopping;
- use fake MEGA/proxy fixtures for deterministic CI;
- do not use real credentials in tests;
- run `go test -race ./...` before any phase that touches concurrency is considered complete.

Release hardening additionally requires `govulncheck ./...`, frontend frozen install/check/test/build, Playwright, resource benchmarks, license audit, and the opt-in live MEGA compatibility smoke.

## Git / editing

- Keep diffs coherent and scoped to the current phase.
- Do not rewrite `PLAN.md`, `PLAN-UPLOAD.md`, or `PLAN-STREAMING.md` during normal implementation.
- Generated files may be regenerated by their owning tools.
- Do not commit secrets, real MEGA URLs containing private keys, credentials, local databases, partial downloads, or build artifacts.
